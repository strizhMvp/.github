# Правила разработки СТРИЖ

## Структура веток

```
main  -- версия банка. Через отдельные hotfix PR или согласованный релиз из dev.
  dev -- интеграционная. Только через PR из feature/fix/chore/refactor.
        feature/<название>
        fix/<название>
        chore/<название>
        refactor/<название>
```

Работа всегда ведётся в отдельной ветке, созданной от `dev`.

Исключение для общего репозитория `.github`: ветки `dev` нет, поэтому ветка задачи создаётся от `main`, PR направляется в `main`; создавать `dev` ради этого не нужно.

| Ветка | Стенд | Что в ней |
|-------|-------|-----------|
| `dev` | https://dev.strizh.vonudog.ru | Разработка. Ветка по умолчанию, каждый мерж сразу выкатывается на dev-стенд |
| `main` | https://strizh.vonudog.ru | Версия, поставленная банку. Меняется только хотфиксами поставки и при выпуске новой версии, согласованной с ИБ |

## Начало работы над задачей

```bash
git checkout dev
git pull origin dev
git checkout -b feature/название-задачи
```

## Именование веток

| Префикс | Когда использовать |
|---------|-------------------|
| `feature/` | Новая функциональность |
| `fix/` | Исправление бага |
| `chore/` | Инфра, зависимости, конфиги |
| `refactor/` | Рефакторинг без изменения поведения |
| `docs/` | Документация |

Примеры:
```
feature/auth-login-endpoint
feature/confluence-page-fetch
fix/jwt-token-expiry
chore/docker-compose-setup
```

## Коммиты - Conventional Commits

Формат: `<тип>(<область>): <что сделано>`

| Тип | Когда |
|-----|-------|
| `feat` | Новая функциональность |
| `fix` | Исправление бага |
| `chore` | Инфра, зависимости |
| `refactor` | Рефакторинг |
| `test` | Тесты |
| `docs` | Документация |

Примеры:
```
feat(auth): добавить эндпоинт JWT-логина
fix(generation): обработать пустой ответ LLM
chore(infra): добавить MongoDB и Redis в docker-compose
test(auth): юнит-тесты для bcrypt-хеширования
```

## Правила Pull Request

1. PR открывается из твоей ветки в **`dev`** (не в `main`); для фичи с собственной интеграционной веткой — в неё
2. Название PR - в формате Conventional Commits
3. Описание: что сделано, как проверить и `Closes <репозиторий>#N` связанной задачи
4. Применимые существующие локальные проверки должны пройти: lint, type check, tests, build — по изменённому пути, а не весь набор для правки документации. В PR публикуются команды, фактические результаты, ограничения, проверенные SHA и ссылки на результаты независимого ревью; зелёные Actions не являются условием мержа.
5. Приёмку выполняет владелец после локальных проверок, двух опубликованных независимых `pass` и закрытия P0/P1. В команде только владелец и помощник: отдельный второй разработчик и формальный GitHub-аппрув не требуются. Разрешённый владельцем scope фиксируется в PR; self-check не заменяет независимые проходы.
6. Merge: **Squash and merge**
7. После мержа - ветку удалить

## Небольшие PR

Весь код вливается небольшими PR — так их реально прочитать, а откат не тянет за собой чужие изменения.

- **Одна задача — один PR.** Большая задача режется на несколько PR, каждый собирается и проходит тесты сам по себе.
- **Ориентир — до 400 изменённых строк**, lock-файлы не считаются. Превышение отмечается в PR при локальной оценке diff относительно целевой ветки.
- **Больше 800 строк — мерж запрещён.** Исключение (сгенерированный код, перенос файлов) согласуется с ревьюером и отмечается меткой `large-pr`. Размер и исключение проверяются до мержа без size-job.
- В одном PR не смешиваются рефакторинг, исправление бага и новая функциональность.
- Черновик (`Draft`) — пока работа не готова; ревью начинается, когда PR переведён в «Ready for review».

## Независимое ревью

Claude/Anthropic больше не используются (решение владельца, 23.11.2026).
Критерии перенесены в [REVIEWING.md](REVIEWING.md), инструкции помощнику — в
[AGENTS.md](AGENTS.md). Ревью выполняется здесь, в рабочем процессе Orca/Codex:
результат с проверенными сценариями, вердиктом и точным head SHA публикуется в соответствующем PR.

Независимые техническое ревью и проверка полноты исходного запроса обязательны.
В PR нужны публичные ссылки на оба результата: `pass`, `needs_changes` или `blocked`,
команды и фактические результаты, непроверенные live-границы. Изменения после ревью
требуют проверки затронутой части на новом head SHA; неизменённые доказательства
переиспользуются. Локальный self-check не заменяет независимые вердикты.
До мержа оба независимых результата должны быть `pass`; `needs_changes` и `blocked`
не разрешают мерж.

По решению владельца от 24.11.2026 команда — только владелец и помощник
(«не существует второго разраба, только я и ты»). Приёмка остаётся за владельцем;
требование аппрува несуществующего второго разработчика и формального GitHub-review
снято. Для работы, которую владелец поручил и разрешил принять, помощник может
выполнить merge после двух независимых `pass` и релевантных локальных проверок.
Запрос владельца, разрешённый объём, результаты и точный head SHA фиксируются в PR.
Это не разрешение на посторонние изменения, обход branch protection, мерж с
`needs_changes`/`blocked` или непроверенный production effect. Dev→main и
согласование release/ИБ сохраняются. Самопроверка автора не является независимым ревью.

### Локальные доказательства вместо CI

Используются существующие команды проекта, без нового runner или фиктивного статуса.
Ниже — сохранённые команды снятых CI; выбирать применимые к изменению:

| Репозиторий | Команды из его корня |
|-------------|---------------------|
| `strizh-shared` | `ruff check strizh_shared tests`; `mypy strizh_shared`; `pytest tests/ -v --tb=short` |
| `strizh-generation-service` | `python -m strizh_shared.scripts.check_team_id app/ --models Generation,TestCase,JudgeVerdict,Log,CritiqueReport,PipelineArtifacts,ExternalTestCase,JiraLink,ActualizationRun,ImportChunk`; `pytest tests/ -v --tb=short` |
| `strizh-integration-service` | `pytest tests/ -v --tb=short` |
| `strizh-pipeline-service` | `ruff check strizh_pipeline tests`; `pytest tests/ -v --tb=short` |

Окружение и зависимости берутся из существующих файлов проекта. Для сервисов,
зависящих от соседних репозиториев, в доказательстве фиксируются их совместимые SHA;
нельзя подменять согласованный срез произвольной версией `strizh-shared` или generation.
Для остальных путей применяются их существующие lint/type/tests/build-команды.
Если проверка неприменима, в PR записывается причина, а не выдуманный успех.

Live golden/eval остаются отдельными существующими сценариями generation:
`python tests/golden/_scaffold/diff_runner.py --threshold-pct 5`
при настроенном dev-доступе и `STRIZH_*` окружении; в работающем dev-контейнере —
`python tests/golden/actualization/eval_runner.py --max-drop 0.05`.
Они требуют реальных dev/Confluence/LLM и разрешённого доступа; запуск с локальной
машины не превращает их в герметичные unit-тесты. Отсутствие такого доступа
отмечается как непроверенная live-граница; удаление расписания не доказывает качество модели.

Dev/prod deploy, их триггеры и tracker сохраняются. Снятие CI не исправляет billing
и не гарантирует успешный deploy. Не менять secrets/settings и не перезапускать
известный сбой до старта ради нового «зелёного» результата. Если required check
реально блокирует merge, сообщить точный блокер без admin bypass или фиктивного статуса.
Отказ доступа к protection/rulesets (например, 403) не доказывает отсутствие защиты.

## Merge dev в main

- Только когда новая версия согласована с ИБ банка: `main` — это то, что стоит у банка
- Только через PR с аппрувом
- **Merge commit** (не squash) - сохраняет историю
- Только после тестирования на dev-окружении
- Поставка для DevOps банка собирается из `main` (или release-ветки этой версии), никогда из `dev`
- Ставим тег версии: `v0.1.0`, `v0.2.0`, ...
- Мерж в `main` может запустить production deploy и требует явного разрешения владельца на этот эффект; такое разрешение не отменяет аппрув и согласование релиза/ИБ.
- Для согласованной поставки исправлений переносить только её изменения отдельными PR из `dev` в `main`, не весь накопленный `dev`. Архив собирать из точных девяти `origin/main` после разрешённых merges; фиксировать SHA каждого репозитория, состав и SHA-256, без dirty checkout или overlay.

```bash
git tag v0.1.0
git push origin v0.1.0
```

## Hotfix - срочный фикс в продакшне

```bash
git checkout main
git pull origin main
git checkout -b hotfix/описание-проблемы

# Фиксишь, коммитишь, пушишь
git push origin hotfix/описание-проблемы

# Открываешь PR в main (с аппрувом)
# После мержа в main - ОБЯЗАТЕЛЬНО мержишь и в dev
```

---

## Что запрещено

- Прямой пуш в `main` или `dev`
- `git push --force` в `main` или `dev`
- Мерж без аппрува или явно записанного исключения владельца для конкретного PR
- Мерж без успешных применимых локальных проверок, независимых вердиктов и закрытия P0/P1 либо с неразрешённым блокером required check
- Коммит секретов, паролей, `.env` файлов
